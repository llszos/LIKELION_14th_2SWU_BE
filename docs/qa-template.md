# 곁 백엔드 QA 시트 템플릿

## 1. 사용 목적과 작성 규칙

기능별 재현 절차와 기대 결과를 공유하고, 실제 검증 결과·이슈·재검증 이력을 남기기 위한 양식입니다. 이 문서를 추가한 것은 QA를 실행하거나 기능 구현을 완료했다는 의미가 아닙니다.

- 각 기능 담당자는 자신의 기능에 대한 사전 조건·테스트 절차·예상 결과와 명세 링크를 작성합니다.
- QA 실행자는 실행 환경·검증 커밋·실제 결과·테스트 결과를 기록합니다. 기능 담당자와 실행자는 다를 수 있습니다.
- 미실행과 기능 실패를 구분합니다. 실행하지 않은 케이스를 PASS나 FAIL로 표시하지 않습니다.
- 명세가 불확실한 항목은 **명세 확인 필요**로 남기고, 합의 전 예상 결과를 임의로 확정하지 않습니다.
- 구현 상태와 테스트 결과는 별도로 기록합니다. 구현되었다는 이유만으로 PASS로 표시하지 않습니다.
- 구현 상태는 `확인 필요`, `미구현`, `준비 코드만 존재`, `실행 가능한 구현 존재` 중에서 확인한 사실을 기록합니다. PR 생성이나 코드 병합만으로 전체 기능 완료를 단정하지 않습니다.
- 상황 이벤트 record는 전달 데이터 계약입니다. 실제 발행 Service·Listener·요청 정리·권한 회수 구현이 있어야 연동 QA를 실행할 수 있습니다.
- 테스트 ID는 예를 들어 `QA-B-F04-001`처럼 영역·기능·일련번호를 조합합니다. 연동 케이스는 `QA-INT-001`처럼 여러 영역을 표시합니다. 이는 이 양식의 제안 규칙입니다.
- 실행 회차별로 양식을 복사해 사용하고, 기준 브랜치·커밋과 재검증 기록을 남깁니다. 동시 실행 결과를 덮어쓰지 않습니다.
- 비밀번호·JWT/접근 토큰·실제 개인정보·민감정보 원문을 시트·로그·화면 증빙에 기록하지 않습니다. 테스트용 가상 데이터를 사용하고 증빙은 비식별 처리합니다.

- 테스트 ID: QA-B-F04-001
- 영역·기능 번호: B / F-04 (복사 후 해당 기능으로 변경)
- 명세 링크: 미기입
- 구현 상태: 확인 필요
- 기능 담당자: 미기입
- 실행자: 미기입
- 검증 브랜치·커밋: 미기입
- 사전 조건: 명세 확인 필요 — 계정·관계·상황·요청·권한 상태와 필요한 구현을 기재

**수행 절차**

1. 명세 확인 필요 — 준비할 테스트 데이터와 시작 상태 작성
2. 명세 확인 필요 — 호출할 API 또는 수행 동작 작성
3. 명세 확인 필요 — 응답·상태·권한을 확인할 방법 작성

**예상 결과**

- HTTP 상태·응답 JSON: 명세 확인 필요

## 5. 결과 상태 정의

| 결과 | 의미 | 기록 기준 |
| --- | --- | --- |
| NOT_RUN | 미실행 | 테스트를 아직 수행하지 않음. 명세·구현 확인 대기도 실제 실행 전에는 이 상태로 기록 |
| PASS | 예상 결과와 일치 | 합의된 기준으로 실제 실행·관찰한 경우에만 사용 |
| FAIL | 예상 결과와 불일치 | 실행 결과가 명세와 다름. 재현 절차·실제 결과·이슈를 함께 기록 |
| BLOCKED | 환경 또는 의존 기능 문제로 실행 불가 | Docker·서버·DB·계정·Listener 등 필요한 조건이 없어 진행할 수 없음. 구체적 원인 기록 |
| N/A | 검증 대상 아님 | 이번 환경·회차·기능에 적용되지 않음. 사유 필수 |

Docker 문제로 통합 테스트가 시작되지 않은 것은 기능 자체의 FAIL이나 PASS가 아닙니다. 환경 오류를 BLOCKED로 기록합니다. `build -x test` 성공도 테스트 PASS의 근거로 사용하지 않습니다.
